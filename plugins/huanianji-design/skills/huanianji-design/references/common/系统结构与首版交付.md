## 1. 第一版最终应该带来什么

长期目标沿用[共同设计规则](华年集共同设计规则.md)：供维护者与 AI 长期使用，帮助不同项目形成合适方向、实现可用的跨平台界面，并积累可复用经验。

第一版完成后，应能在 Codex 中实际走通这样的使用过程：

1. 维护者说明要做什么产品或界面，AI 读取系统和当前项目的相关资料。
2. 新产品获得有实质差异的设计方向；已有产品延续已认可主题。
3. 维护者能通过具体画面与操作选择和修正方向，AI 将选择落实到界面。
4. 关键控件在不同产品主题中保持共同身份与操作手感，并在首批目标平台分别运行。
5. 交付时有实际检查结果；后续新增页面或更换会话，能从项目档案接续决定。

这条过程是首版验收的主线。共同规则、组件、示例和调用入口分别为它服务，不能以某一份文档或展示页完成替代整个第一版完成。

## 2. 整体结构：各部分分别负责什么

| 模块 | 职责 | AI 在什么时候读取 | 与其他模块的边界 |
|---|---|---|---|
| AI 调用入口 | 说明适用任务、读取顺序、任务分支和输出要求 | 每次调用时读取简短入口，再按任务进入细节 | 负责组织工作；不重复全部品牌规则、平台文档和组件源码 |
| 共同设计语言 | 定义华年集身份、必须统一/产品自由的边界及共同交互性格 | 新方向、界面实现、相关评审时 | 当前单源为共同设计规则；产品业务规则继续由各项目维护 |
| 方向探索方法与产品档案 | 帮助新项目形成方向，保存已有产品的主题、决定与未决问题 | 新产品、明确改版或已有产品继续设计时 | 方法可以共用；每个项目的具体决定保留在该项目单源 |
| 令牌与主题 | 将颜色、字体、形状、尺寸和运动角色表达为可引用数据 | 需要实现或调整视觉时 | 值只维护一处；主题引用角色，平台负责映射，不另外手写多份相同数值表 |
| 交互模式与组件说明 | 描述控件解决什么问题、状态、输入、触发、运动、中断与恢复 | 只读取本次需要的模式 | 共同描述行为与意图，不把 React 代码当所有平台的实现 |
| 平台适配与实现 | 把共同意图落到 Web、桌面、iOS、Android、Godot | 读取当前目标平台及所需实现 | 平台分别实现，明确可运行范围和验证状态 |
| 实际示例与评审依据 | 展示界面、操作、状态、主题差异及已知问题 | 方向比较、实现参考和实际检查时 | 示例消费同一实现；合成演示、正式产品与实际验收分别标明 |
| 复用经验与维护记录 | 保存认可案例、失败原因、适用条件和规则变更依据 | 与当前任务相关时读取，交付后按授权更新 | 当前项目经验先留在项目中；提升为全产品规则需要明确确认 |

建议将这些内容组织成一个可携带的本地文件包。AI 入口是使用方式，其他模块是持续维护的设计内容与实现资产；未来可以按需求增加分发工具。

## 3. AI 入口怎样设计

### 3.1 一个主入口，按任务分支

建议第一版先设一个聚焦于华年集界面设计工作的主 Skill。其入口只保留：适用范围、共同约束的入口、读取路线、任务分支、必要检查和交付要求。

OpenAI 官方资料说明：Skills 将说明、资源及可选脚本组织在目录中；模型先看到名称与描述，需要时再读取完整 `SKILL.md`。该机制适合本系统按需读取的设计。P1 已在本机独立 CLI 调用中验证显式与自然语言调用，具体证据见阶段记录；自然语言匹配仍不保证每次命中。来源：[Build skills](https://learn.chatgpt.com/docs/build-skills)。

建议的任务分支：

| 分支 | 典型需求 | 主要读取 | 本次应该形成什么 |
|---|---|---|---|
| 新产品或明确改版 | 「帮我设计一个素材管理工具」 | 共同规则、方向探索方法、目标平台、相关模式和参考 | 设计简报、可比较方向、选择依据及对应实现或设计草案 |
| 已有产品继续设计 | 「按米鹿工坊现有方向加一个素材详情」 | 已有产品设计档案、相关共同规则、目标平台与组件 | 保持主题的新增界面、相关状态、检查结果及档案更新 |
| 局部精修或修复 | 「这个 Tab 切换不连贯」 | 原有决定、具体实现、选择/切换模式、平台约束 | 聚焦问题的改动或诊断；不重新设计整个产品 |
| 设计检查 | 「检查这一页是否符合共同规则」 | 本次评审范围、产品档案、共同规则及实际界面 | 具体发现、位置、证据和取舍建议；只检查时不自动实施 |

P1 主入口为 [huanianji-design](../../SKILL.md)，界面名称「华年集设计系统」，本机通过 `~/.agents/skills/huanianji-design` 符号链接引用项目源。自然语言与显式调用按实际记录核对；本稿不修改全局配置。

### 3.2 读取路线

建议读取顺序为：**任务与项目规范 → Skill 入口 → 本次相关共同规则 → 产品档案 → 目标平台 → 所需主题/模式/实现/案例**。

先检查当前项目是否已有认可方向。已有决定能回答的问题直接沿用；只有会改变产品身份、任务结果或范围的缺失信息才向维护者提问。

每次不需要读取整个参考库、所有平台或所有组件。若所需组件/平台尚未具备，明确缺口并提出本次可执行的适配方案，不宣称已有支持。

### 3.3 每次调用的产出与接续

| 阶段 | 需要解决的问题 | 应保存或交付的结果 |
|---|---|---|
| 理解 | 用户、内容、主要操作、场景和平台是什么；本次授权到哪一步 | 简要需求与验收要求，优先补进已有任务/项目记录 |
| 选择方向 | 当前主题是否适用；新方向怎样兼顾品牌与产品调性 | 方向及取舍、共同特征、产品可变部分、维护者的具体选择 |
| 实现 | 用哪些现有资产和平台能力，怎样覆盖必要状态 | 可操作界面、清楚的状态与输入、素材和实现来源 |
| 检查 | 实际画面与操作是否符合目标 | 实测范围、结果、截图/录屏和仍未解决的问题 |
| 沉淀 | 哪些经验能供下一次使用 | 更新当前产品单源；有普适价值的发现提出为共同资产候选 |

实现任务按已授权范围连续完成；讨论或检查任务停在对应边界。方向探索应展示界面中的布局、控件、素材和实际操作，不能仅用品牌登场或替换颜色代表不同设计方向。

### 3.4 经验积累的具体含义

记录保存在文件中，后续会话重新读取。它不依赖模型记住上一段聊天，也不承诺自动学习。

当前任务已确认的决定、事实和检查结果写入该项目现有设计档案；未选方向和失败实验标明状态。AI 可以在本次获授权的文档工作中记录这些内容。改变共同规范或把实验提升为全产品默认值时，需要维护者明确确认。

个人全局记忆、其他项目规范、安装中的 Skill 副本和发布状态分别管理；普通项目经验不自动改写它们。

## 4. 文件与实现怎样组织

以下是完整文件包的逻辑结构示意，不表示每个目录和能力已经存在。P1 的实际文件与状态见主入口及其资源清单；尚未创建令牌、公共实现和主题的空目录。

```text
huanianji-design/
  SKILL.md                         AI 主入口与读取路线
  references/
    common-rules.md                共同规则的正式单源
    direction-guide.md             方向探索与比较方法
    patterns/                      交互含义、状态、输入与运动规则
    platforms/                     各平台适配要求与支持边界
    product-index.md               产品档案入口及主题引用
    cases/                         已认可或待核案例的索引与说明
  assets/
    tokens/                        共享角色与主题数值
    implementations/
      web/                         Web 可运行实现
      godot/                       Godot 可运行实现
    examples/                      使用公共实现的操作和主题示例
    brand/                         已确认的品牌资产及使用说明
  scripts/                         确有需要的引用、令牌等检查
```

组织原则：

- 当前[共同设计规则](华年集共同设计规则.md)是本阶段单源。正式打包时迁入或映射到确定位置，保留清楚入口；不长期维护两份独立正文。
- 产品的业务与设计决定留在其已有项目单源；文件包保存指向档案的入口、可复用主题和必要示例。独立主题示例与真实产品档案分开标明。
- 当前已按授权采用内部 JSON v1 初版，配合 Markdown 解释角色和取舍，已有 Web CSS/运行数据与 Godot 原生主题生成，见[共同源说明](../shared-foundation.md)。平台输出由同一源产生，不能各自成为另一份可编辑调色板；完整角色/主题范围仍需后续验证。
- 交互模式记录行为，平台实现记录怎样做到；平台特例明确注明，不把某个平台的实现细节写成所有平台的要求。
- 示例引用公共实现，案例保存真实结果与反馈；不为展示效果复制出第二套组件代码。
- Skill 安装副本与可编辑源区分清楚。使用说明应说明来源与更新方式，避免只改源文件却误以为已更新所有使用处。
- 检查脚本只承担明确可机械判断的工作，例如引用能否解析、令牌缺失、示例能否运行；品牌好坏与动效手感保留实际评审。

本地文件与资源已经足以设计首版的调用方式。官方资料明确 Skill 可以在不需要实时数据和受控操作时独立工作；MCP 用于提供实时信息与受控动作。第一版建议先使用文件包，未来根据实际需求再讨论工具接口。来源：[Skills](https://developers.openai.com/plugins/concepts/skills)。

## 5. 第一版交付清单

第一版以「能实际用于新项目，并能跨会话接续」为已确认完成标准，首批可运行平台为 Web + Godot。以下清单用于落实这一标准，具体实施细节仍需按路线确定；暂停的加载与进度切片不因该确认而恢复。

| 编号 | 第一版交付 | 交付内容 | 完成依据 |
|---|---|---|---|
| D1 | 可调用的主 Skill 与使用说明 | 简短入口、读取路线、任务分支、资源定位、安装/调用/更新说明 | 在实际 Codex 环境中能发现并调用；用真实需求验证所读内容与产出，不仅检查文件格式 |
| D2 | 共同语言与最小品牌识别规范 | 完整共同规则；产品自有名称/Logo 的引用；普通文字「华年集出品」及共同字体/形状/动态用法；软件内不展示母品牌 Logo | 必须统一、产品可变和平台差异明确；正确使用已有标识与文字，实际界面中可辨认产品及归属；不以新做 Logo 为验收前提 |
| D3 | 方向探索方法与产品档案模板 | 从任务到设计方向的方法、比较维度、主题记录和项目接续要求 | 新产品能提出实质不同且适合任务的方向；已有产品能延续主题并新增界面 |
| D4 | 令牌与可变化的主题 | 可读取的角色、数值与引用关系及 Web/Godot 映射；管理/创作两类均有白/浅灰与黑/深灰背景及切换，强调色独立可调 | 切换不需重写组件行为，基础背景保持中性、内容/状态保持；引用无缺失，双端输出与源数据关系清楚 |
| D5 | 六类偏好的共同基线 | 字体；按钮回弹；Tab/分段；动态图标；输入焦点与验证码；内容展开/收起的规则和参考实现 | 每类覆盖真实用途及必要状态；保留原始参考，说明打磨差异和适用边界 |
| D6 | 首批平台适配 | Web + Godot 的可运行基线与使用说明；桌面、iOS、Android 的适配要求及当前支持状态 | 两个首批平台分别运行并检查共同意图；未运行的平台准确标待适配，不能以文档覆盖冒称支持 |
| D7 | 日常操作展示与主题对照 | 一个可定位的操作展示入口；管理与创作两类有明显差异的小界面，均可切换浅深中性背景；验证码可作为独立输入示例 | 实际比较触感、切换、图标、输入和收展；两类在内容组织上有区别，切换背景不丢当前操作；不强行把全部组件塞进同一流程 |
| D8 | 完整使用验证与第一批复用记录 | AI 从需求到界面的使用记录、已有主题扩展记录、跨平台与新会话接续证据、认可案例与失败记录 | 按第 6 节验证；另一会话能通过文件延续选择，复用内容有来源、状态与限制 |

D5—D8 可以复用同一套公共实现、示例页面和验证项目，不要求重复建多套演示应用。验证项目可以独立于正式业务仓，避免将业务迁移混进设计系统建设。

### 第一版跨平台覆盖的精度

Web 与 Godot 都应实现用于验证的共同基线。某个模式在目标平台不合适时，提供保持相同意图的替代并实测，不能只留空目录。

首版覆盖有限的交互与界面范围，不承诺每个平台的完整控件库。Web 页面在桌面或手机浏览器可运行，也不自动视为已完成桌面原生、iOS 或 Android 适配。

如果目标引擎、设备或检查条件不足，该部分保持待验收；不能在交付时悄悄改成文档以宣布 D6 完成。实施前需核对具体技术和运行条件。

### 第一眼辨识度怎样处理

维护者已明确：各软件与华年集均有自己的 Logo，软件内不体现华年集 Logo。家族联系通过共同字体、A 的界面形状、留白、视觉对齐和运动形成，普通文字「华年集出品」说明归属；产品身份使用本产品既有 Logo。第一眼的家族联系仍需在不同产品方向的实际界面中判断，不能仅凭文档宣称成立。

最小规范覆盖已有产品资产引用、文字排版与共同设计语言，不要求重做母品牌/产品 Logo、完整企业 VI、角色世界观或衍生品品牌手册。母品牌 Logo 的来源见[共同规则 §3.7](华年集共同设计规则.md#37-现有标识与历史提案)，不用于软件；旧登场实验和已终止的三个图记提案都不能作为正式标识或后续制作前提。

### 第一版暂不纳入的交付

- 五个平台的全量成熟组件库，以及所有现有产品的批量迁移。
- 独立可视化设计工作台、在线资产管理平台和实时 MCP 检索服务。
- 跨产品账号、支付、业务数据互通或正式业务接口重构。
- 大型风格数据库、完整插画/3D/音效生产线、动漫与游戏内容本身。
- 无需维护者确认就自动改写共同规则的机制，以及云端发布、付费资源或公开分发。

它们可在明确需求出现后另行决定。第一版保留扩展边界，重点完成上述实际使用过程。

## 6. 第一版怎样验收

下列是完整第一版的验收场景。P1 仅完成入口、档案与运行条件的对应部分，不代表下列场景已整体完成。

| 场景 | 应验证什么 | 需要的证据 |
|---|---|---|
| 新项目从需求到界面 | AI 按需读取，理解任务，形成不同方向，在选择后实现主要操作和必要状态 | 实际调用、所用规则与来源、方向比较、可运行界面与检查记录 |
| 已有产品继续设计 | AI 能找到已认可档案，不反复询问既定选择，不无故换主题 | 新增界面与原主题的对照、沿用/新增决定、实际操作结果 |
| 主题差异与共同身份 | 管理与创作两类界面在布局、素材或动态表达上有差异，仍可指认共同来源 | 相同核心控件的对照、母品牌表达、维护者的具体反馈 |
| Web 与 Godot | 按压、选择、图标、输入和收展等共同意图分别成立 | 两端运行入口、技术/版本、输入与状态检查、截图或录屏及差异说明 |
| 关键交互质量 | 连续点击、反向操作、失败恢复、焦点、文字阅读及减少动效可用 | 适用场景实测；自动检查与人工视觉判断分别记录 |
| 新会话接续与复用 | 不依赖原聊天，能从产品档案和系统资源延续设计，再使用已认可组件或经验 | 新会话中的实际任务、读取来源、延续结果和仍需补齐的信息 |

第一版状态应逐项标为完成、失败或待核，附证据和限制。标识清楚不等于仅凭外观已建立辨识度，运行成功不等于视觉获认可，Web 验证不能替代 Godot 验证。

正式产品接入、真实数据与外部服务的验收，需按该项目真实目标另行验证。首版不能以模拟按钮成功代替这些结果。
