## 1. 从哪里开始，以及为什么

建议先做**可实际调用的 AI 入口、项目设计档案与验收准备**，并核对 Web/Godot 的运行条件。

理由是：第一版要让 AI 能找到规则、延续项目决定并实现界面。先建立读取与记录的最小过程，后续字体、形状、运动、主题和平台差异才有稳定的使用入口。入口随真实资产逐步完善，不提前写成包含全部资料的长提示词。

随后按依赖推进：

**入口与接续 → 共同视觉与令牌 → 两端交互基线 → 主题及综合场景 → 新项目与新会话终验。**

Web 与 Godot 按交互逐项配对实施，先在两端贯通按钮、选择和展开，再扩展图标与输入。这样能在共同模式仍容易调整时发现平台差异，减少后续返工。

## 4. P1：先让 AI 能读取、记录和接续

### 交付物

- 一个聚焦华年集设计任务的主入口初稿，能区分新产品、已有产品继续设计、局部精修和只读检查。
- 与现有共同规则连接的读取路线；资源清楚标记为可用、实验或未实现，不建立看似完整的空资源目录。
- 项目设计档案模板：用户与任务、目标平台、视觉方向、已确认选择、自由范围、组件/主题来源、检查结果、未决问题与下一步。
- Web 与 Godot 的实际运行条件记录：目标技术/版本、运行与查看入口、字体与输入检查方式、可用设备及待补条件。具体版本在本阶段核对，当前不预设。
- 固定的验收需求与任务集合，覆盖新项目设计、已有主题扩展、局部精修和新会话接续。

### 验收门槛

1. 实际调用入口能够定位当前规则和目标项目档案，按任务读取相关内容，不要求维护者粘贴全部历史聊天。
2. 新任务能形成可供后续使用的设计简报；已有项目能读取既定决定；只读检查任务保持对应边界。
3. 当前缺少的实现、平台能力和视觉决定被准确列出，不能产出「已支持」的假状态。
4. 初步使用不携带原聊天历史的验证上下文，只检验档案可读与决定可恢复；P5 再验证真实界面的完整延续。
5. 能说明两端后续如何实际运行与检查。设备或引擎条件有缺口时，继续不依赖它的入口/档案工作，相关平台验收保持待核。

本阶段的价值是可用的设计组织与接续能力，尚不表示六类组件或跨平台界面已经完成。

2026-10-26 执行结果：P1 五项门槛按本机入口、档案和技术运行范围通过。圆桌后的入口/引用/路径修正、档案精简与已选方向局部写回已完成；证据及未覆盖条件见 [P1 验收记录](../packaged-status.md)。后续先讨论 P2，本轮不进入第二阶段实施。

在 P1 记录一个有实际用途、范围清楚且区别于 Gallery 的独立需求。它应包含能够完成的操作，能检验系统是否帮助形成方向和实现界面；不为了测试临时扩大成完整业务平台。

具体项目简报在实施准备时确定。需要文件、API或持久化的能力按简报验证真实路径；合成数据可以用于检查 UI，但不能代替这些能力的可用证据。

### 必须取得的证据

| 验收任务 | 通过标准 | 证据 |
|---|---|---|
| 从新需求到界面 | AI 通过入口读取规则，形成适合任务的方向，落实选择并完成约定操作 | 原始简报、读取来源、方向选择、实现入口与主路径检查 |
| 两端运行 | Web 与 Godot 分别完成首版约定的共同操作，平台差异明确 | 技术/版本、运行记录、实际输入/状态检查及画面/录屏 |
| 新会话继续项目 | 不含原聊天历史的会话能定位系统与项目档案，准确延续已有决定，并完成一次新增或修改 | 新会话输入、读取来源、延续决定、实际变更与检查结果 |
| 经验复用 | 后续任务找到并使用先前认可的组件、主题或经验；试验与共同规则的状态没有混淆 | 复用来源、适用条件与新任务中的实际结果 |
| 交付可用 | 可定位源包与调用方式，安装/更新关系清楚，必需项没有以空目录或说明代替实现 | 使用说明、资源清单、D1—D8 逐项结论与已知限制 |

跨会话测试不能通过在原会话中假装忘记、粘贴完整历史聊天或提供预设答案来替代。使用实际不含原历史的验证上下文，按执行环境与授权采用可用方式，并记录方法。P1 采用独立的临时 Codex CLI 会话，没有创建侧边栏聊天或调用子代理。
