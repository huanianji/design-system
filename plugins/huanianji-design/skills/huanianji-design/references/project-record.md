# 项目设计档案的使用

## 定位单源

优先读取用户明确指定的设计档案。否则依次检查项目根目录 `PROJECT-DESIGN.md`、`DESIGN.md`、`docs/design.md`。已有入口应复用；多个内容冲突时核对用途，不创建第二份独立裁决。

`context` 和 `init-record` 只探测这三个默认名称，不负责发现任意自定义档案。用户指定其他文件时直接读取并维护该文件，不将“没有默认档案”解释为“项目没有档案”。

新项目尚无档案时，可使用模板创建 `PROJECT-DESIGN.md`。需要写文件时遵循本次任务范围；只读任务只报告。若执行环境只允许读取，可输出完整待保存内容并说明由调用方保存，不能声称已写入。

区分生成时与保存后的状态。由调用方保存输出时，将当前档案标记为已保存，注明保存方式；保留必要的“模型当次只读”事实，但不要继续把已存在的档案列为下一步待保存。原始验证输出可以作为不可变证据另存，不充当第二份项目裁决。

## 档案需要承接的信息

- 产品给谁用、解决的任务、关键内容与本次实施边界。
- 目标平台、技术与运行条件，哪些已验证、哪些待核。
- 已确认的用户选择，以及来源；AI 提出的候选与待确认选择单列。
- 当前主题、字体/形状/动态及内容组织的决定；尚未决定的参数保留待定。
- 继承哪些共同规则，哪些由产品决定，哪些按平台改变。
- 实现入口、复用来源及真实支持状态；没有实现时明确写未实现。
- 本次实际检查、失败及限制，下一次能直接执行的任务。
- 涉及界面实现 / 精修时，按[交互差异排查](interaction-review.md)简短说明受影响部分的操作边界、状态 / 动效归属、平台默认值和允许差异；保存实际操作检查点，避免只有截图终态或测试数量。

记录的事实、建议、确认和验证状态不能混用。引用仍处于讨论阶段的共同规则时，应保留其草稿状态，不将打磨建议写成已经冻结的规范。某一测试或产品选择不改变华年集母品牌规则。

## 保持档案聚焦

当前简报、已选决定、待定项和下一步放在容易找到的位置。系统能力、共同规则和通用运行条件引用各自单源，注明读取日期及对本项目的影响，不每轮复制整张能力表或全部平台检查要求。本项目实际使用的版本、差异、失败和验证仍记录在项目中。

局部续作更新对应段落及必要的下一步，不因新增一个筛选而重新生成全部档案。精简重复说明时保留有效决定；仍有价值的详细论证保留在原说明或明确标注的历史证据中。

## 接续已有项目

1. 读现有档案和相关文件，识别已确认选择、未决事项及下一步。
2. 将新要求与这些决定对照，只调整受影响内容；旧决定未被新要求改变就继续沿用。
3. 同一条决定在其原位置更新；需要解释变化时记录原因和来源。保留仍相关的限制与验证状态。
4. 写入实际完成的检查与下一步，避免只有“继续优化”等无法执行的描述。

用户只要求新增筛选或精修交互时，不重新询问产品名称、已选平台、界面密度或其他已记录选择。遇到真实冲突、缺失或错误记录时说明并核对。

## 跨会话证据

下一次调用只需取得目标项目和本系统入口，就应能读取档案继续。验收时保存前后档案、各次独立调用的输入和实际读取来源；新会话不提供原聊天历史或预设答案。

P1 只验证档案和规则的恢复及更新；P5 才检验已实现界面的真实续作。不得将早期档案接续写成完整产品接续验收通过。
