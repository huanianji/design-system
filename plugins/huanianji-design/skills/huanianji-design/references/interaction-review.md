# 界面细节分叉的定位与复核

用于新界面实现、已有基准的精修、跨平台对照及用户报告“这里又不一样”。不以做完组件目录为前提；从当前任务中的交互职责推导检查。单平台也可将自己的实现与已确认的设计基准对照。

## 实现前明确本次需要保持的关系

在已有项目档案或任务记录中简短写清受影响部分，不为小修另建全套文档：

| 要说明的关系 | 要回答的问题 |
|---|---|
| 内容与视觉边界 | 必须显示哪些字段？外框、背景、图标、文字各承担什么角色？哪些差异可由产品 / 平台决定？ |
| 操作与状态边界 | 一项动作对应整个区域还是若干独立操作？点击、键盘焦点、选中、悬停、禁用分别属于哪个对象？ |
| 状态变化 | 用户通过什么输入触发什么结果？动作进行中再次操作、切主题、改变尺寸或减少动态时如何落定？ |
| 实现来源 | 复用什么、平台分别实现什么？哪些外观来自 CSS / 原生 Theme 继承、系统默认或局部覆盖？ |

这些关系是跨端需要实现的意图，颜色 / 圆角 / 时长令牌是其参数。两个实现读取相同令牌，并不能证明职责、触发路径和显示字段相同。组件尚未入库时，也应根据本次动作说明这些关系。

例如，素材卡片若只有“选择该素材”一个动作，图片和标题应指向同一个操作单元和焦点范围。复杂卡片有多个真实动作时可拆分，分别说明职责；不能把这一案例推广成“所有卡片禁止有子按钮”。

## 顺着因果链查差异

1. **对齐条件。** 核对实际页面 / 场景、设计数据版本、消费端实现摘要、固定内容、窗口、文字倍率、主题、减少动态、输入方式、当前选择和滚动位置。条件不同先记为不可直接比较。设计 `build_id` 只证明其覆盖的源 / 生成物，不能代替消费端代码摘要。浏览器普通刷新也可能继续加载旧JS/CSS；复验先核对页面实际消费的资源，必要时强制无缓存刷新，不能仅对磁盘源码做摘要。

   视口命令返回也不证明当前标签页已收到该尺寸；采集器必须记录实际 `innerWidth/innerHeight` 或原生窗口尺寸，并与约定比较。标签页专属覆盖不能沿用另一个页面的句柄；时间窗采样同时记录经过时间，错过回弹或首帧尚未推进时，不据此判断组件没有动态。
2. **查组成。** 从可见区域走到 DOM / Control 树：装饰容器、可点击区域、可聚焦对象是否承担了预期职责？是否叠出两个操作目标、状态边框或事件处理器？不要先用隐藏边框遮住结构错误。
3. **查状态来源。** 区分选中、键盘焦点、鼠标悬停、按下和禁用；追到实际获焦对象、CSS 选择器、Theme variation / 基类、系统默认和实例覆盖。状态组合也要查，例如选中后悬停、选中 A 却聚焦 B、点击其他区域后旧焦点保留。
   焦点还要分开记录“逻辑归属”和“实际可见提示”。仅有焦点对象名、按钮已解锁或结果文字，不能证明提示正确。异步禁用 / 恢复后，至少检查鼠标触发、键盘触发、处理中键盘转鼠标、处理中导航到别处；前两者分别验证无需残留键盘框和必须保留可见提示，后两者验证当前输入方式及不抢回焦点。浏览器`:focus-visible`、CSS最终outline和Godot隐藏焦点不是同一字段；读取实际显示规则并看画面，不能只比较布尔属性或全局隐藏焦点框。
4. **查事件和运动。** 从真实输入沿命中、冒泡 / mouse_filter、焦点转移、业务状态和视觉反馈检查。相同时长不代表相同动效，直接调用选中函数不能验证点击会走的路径。
5. **查排布与渲染。** 前面的语义一致后，再区分容器、断点、行高、内边距、画布裁切和字体 / SVG 渲染差异。允许的平台差异写明理由；没有依据的分叉保留为未对齐项。

   外框声明尺寸正确仍可能被内部控件的默认最小宽度撑开。检查实际子容器/轨道、末项边界与裁切，不只读根节点的rect或CSS width；数字输入、按钮组、列表和复合编辑区均适用。原生验证码曾出现根范围正常、内部HBox被LineEdit最小字符宽度撑大的情况，已在[输入批记录](packaged-status.md)保存画面并补内层检查。

素材条等重复布局还要读取实际每项宽高、标题对齐、流式/等分策略与筛选组位置。单项内容相同、外框不越界，仍可能把Web的等分大卡片与原生固定小卡片误判为一致；当前合批保留了修复前画面，并补实际布局配对，见[合批记录](packaged-status.md)。

排版差异还要核对使用位置到字体角色的映射、最终字形字重和关键数据是否读全。数字等宽、字号一致或外框不溢出，不代表字重及文字完整性已正确；数据区、输入框和局部标题不能被样本文字的检查代替。切换主题 / 字号后先确认实际生效的字体和布局，再测文字净空，避免读到更新前的缓存。新增字体特性时保留已有字体轴与回退，不依据样式名推断实际字重。本轮反例与复验见[字体圆桌修复](packaged-status.md)。

修复后回到最早产生分叉的层复核，再检查受影响的调用路径。不要以两端代码结构必须完全相同为目标，也不要把平台默认行为自动视作已接受的设计。

运动还必须有明确的内容归属：切换记录、筛选结果或复用绘制节点时，先结束旧内容拥有的动画，再写入新状态。反向操作同一内容时可以从当前视觉值续接；换成另一条内容时，不能让旧 Tween / 回调继续覆盖它。要同时观察业务值与实际图形，例如 CheckBox 为未选中但勾号仍被旧动画画出，也属于失败。这个判断适用于任意复用区域，不限名单或勾选框。

## 由当前交互推导操作路径

从本次实际存在的操作和状态选取代表路径，不要求遍历整个组件目录或机械组合全部状态：

- 同一操作可从不同可见部位触发时，分别点文字、图标 / 图片和边缘；检查是否得到相同结果和交互边界。
- 鼠标点击、移出、再点其他区域；Tab / Shift+Tab、方向键及 Enter / Space，按控件实际支持选择。观察获得 / 离开焦点后的画面，不能为修视觉而取消键盘可达性。
- 对有动态的控件观察按下、长按、松开、极值、落稳和连续打断；对有切换 / 隐藏的控件观察进行中换主题、改尺寸、减少动态、隐藏及恢复。
- 按实际功能覆盖空态、禁用、错误、较长内容或文字放大；本次不存在的状态不虚构为已测。

调用业务函数适合验证数据逻辑；要验证用户操作，就必须走输入事件。至少对重点路径进行工具驱动的真实操作并保存对应画面，程序内断言不能替代这一步。

## 保存“同一步操作”的两端证据

将动作序列、条件、观察到的语义结果和画面配对保存。观察应来自实际 DOM / 节点 / 渲染状态；不要由期望值生成观察结果。行为约定应先于修复，不能为了消除报告而照抄当前实现。

同一检查点至少观察与本次风险相关的内容：显示字段、操作目标数、实际焦点归属及范围、可见状态层、布局 / 命中稳定性或运动极值。数值断言之外，打开配对的实际截图；运动问题还要查看过程或其真实采样。可以做图像差分辅助定位，但不能把字体抗锯齿等像素差异自动当业务问题，也不能靠图像相似就忽略焦点和命中。

区分落稳检查与过程采样：前者等待实际结束条件，不能假定一次工具调用后动画已结束；后者记录采样时间窗，错过中间阶段就记为未观察。先核实采集器的焦点、快捷键、单位解析及重排后的命中坐标，避免把工具错误算成产品缺陷。共享桌面上的两端输入应串行执行；窗口不刷新或证据不完整时，这一批不得判通过。

新项目可按自己的控件声明观察字段，使用 [compare_interactions.py](../scripts/compare_interactions.py) 比较：

```sh
python3 scripts/compare_interactions.py \
  --contract <当前项目行为约定.json> \
  --observations <平台A实测.json> <平台B实测.json> \
  --output <差异记录.json>
```

约定包括 `scope`、共同 `context`、需配对的 `context_keys`、各检查点的 `id/actions/expect`，以及需要两端相等的 `equal_fields`。字段名由项目定义，不限素材卡片；`layers` 只提供定位提示。平台差异应在项目记录中说明，检查只纳入需要保持一致的事实。不要直接把平台差异从记录里删掉来获得通过。

每份实测包括 `platform` 和 `cases`；每个检查点给出实际 `actions/context/observed/screenshot`，并保存消费端及采集器摘要。截图相对记录文件所在目录解析，可用 `evidence_root` 声明相对根；缺少实际文件会报错。参考[素材案例约定](../foundation/sample/media-review.json)、[只读 Web 观察器](../foundation/web/observe-media.js)和[Godot 输入采集器](../foundation/adapters/godot/observe_media_states.gd)。它们只适配当前案例，新控件需要按自己的语义提供观察与输入映射；不能把素材节点名照搬到别的产品。

当前案例可跨会话复跑：用 CUA 依当前浏览器说明绑定正确的 Web tab、临时对齐视口，再调用 [replay-media.cua.mjs](../foundation/web/replay-media.cua.mjs) 的 `replayMediaReview({tab,fs,root,phase})`，其中 `fs` 是 Node 文件 API，`root` 为 foundation 的绝对路径。该适配器只用 CUA 真实点击 / 键盘与只读观察，不直接设置页面选择状态。原生在同一 foundation 运行 `<Godot> --path <foundation> --script res://adapters/godot/observe_media_states.gd -- --phase=<批次名>`。最后运行比较器并打开对应截图；完成后恢复临时视口。复跑无需旧聊天中的变量，先按当前环境工具说明取得句柄。

第二个实际案例使用[管理操作约定](../foundation/sample/management-review.json)：`web/replay-management.cua.mjs` 的 `replayManagementReview({tab,fs,root,phase})` 对应原生 `adapters/godot/observe_management_states.gd`，运行参数同上。另用 `web/replay-management-motion.cua.mjs` 的 `replayManagementMotion({tab,fs,root,phase})` 和原生 `adapters/godot/verify_management_motion.gd` 检查快速换记录、筛选中断、展开反向和减少动态；这些是当前场景的输入映射，不能据此宣称其他产品已经通过。执行结果与保留的平台差异见[片段记录](packaged-status.md)。

比较器分别标记：约定违背、平台事实差异、输入路径被替换、检查点未执行、条件未对齐。两端相同但都违背约定也会失败。它不会控制界面、验证操作记录的真实性、自动理解未声明的视觉细节，或把截图存在视作已经审阅。

## 交付前按实际消费补过程门禁

2026-10-27提交按钮漏检：普通按钮的过程检查通过，不能替代主操作变体在校验拒绝、接受提交和进入处理中时的过程。原输入18点主要观察结果，遗漏在途状态重置回弹和局部主按钮样式覆盖禁用态；因此当时的“一致”结论越过证据范围。

本次实现/修改交互时，先从实际消费者列出「交互角色 × 使用的变体 × 业务分支 × 输入/中断方式」；只选本次真实存在的组合。按一个普通按钮推断所有变体，或把校验未通过的一次点击当作提交路径，都不能覆盖它们。除声明的规则外还要查看实际过程画面，未知视觉差异不能由比较器自动保证。

对存在运动的消费路径，保留真实输入前、按住、释放、状态切换、极值与落稳的采样，并同时观察逻辑阻断、颜色和命中。正常回弹、显式不可用、业务在途是不同的生命周期；接受本次输入后，不能为阻止下一次提交而清掉应保留的释放反馈。平台原生激活时机有差异时明确记录，不能任意拉伸时间获得一致。

当前可复用的采集机制是[Web逐帧观察器](../foundation/web/observe-button-motion.js)与[Godot按钮观察器](../foundation/adapters/godot/observe_button_motion.gd)。前者观察当前已绑定公共行为的实际按钮事件和渲染属性；后者的事件/属性采集可复用，但run内的场景与准备动作只适配本批，不能照搬节点名充作新项目覆盖。Web只在显式开发采集地址加载，不进入正常用户流程。

本批[消费约定](packaged-status.md)和[过程门禁](packaged-status.md)检查两端自身是否符合共同角色，再比较实际曲线与外观；两边同样没有回弹也判失败。缺少分支、采样断档、页面实际资源不符或源码更新后沿用旧记录，均不能通过。它已接入本批输入与首批公共交互的收据脚本，不能仅凭结果状态生成通过收据。新的产品/页面须重新声明自己的实际消费范围与准备动作，不能借本演示的通过结论覆盖新界面。修复前反例、修复后记录及[实测曲线](packaged-status.md)一起保留。

## 交付与后续复用

报告已核实根因、改动层、实际覆盖路径、明确保留的平台差异和缺口；测试数量不代表已排查所有界面。对照修复前可复现失败和修复后通过，证明检查确实能抓到这个问题。

可复用的判断放在本流程，产品差异和实例证据留在项目档案，正式复用代码按组件阶段推进。新问题先归因到边界、状态、继承、事件、排布或运行条件，避免每遇到一个控件就增加一条全产品视觉禁令。
